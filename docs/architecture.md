# Clicky architecture

Clicky is a native Qt Quick Wayland application backed by a private Python worker. No HTTP control server is exposed by the application. C++ manages window lifecycle, single-instance local IPC, theme/language integration, process supervision and local TTS; QML provides the functional interface. Python owns the agent, persistence and official MCP SDK. This additional worker is justified by the maintained SDK and keeps the UI independent of providers and tool transports. The installed Qt toolchain avoids Electron and additional system packages. Application directories are modular rather than forcing all agent logic into the native UI.

## Data and trust boundaries

The frontend spawns one worker and exchanges bounded JSON lines over inherited pipes. User secrets travel only through these pipes and are stored with GNOME Keyring, or supplied by explicit environment-variable references. Configuration contains endpoints, model identifiers, capability-probe results, allowlists and secret references, never keys. No existing Codex/Claude credentials are reused. Sensitive payloads are excluded from diagnostic logs. Local conversation data is private (0700 directory / 0600 files), but is not encrypted at rest; protect it with the system disk encryption and user account.

SQLite migrations run transactionally with foreign keys, WAL and explicit schema versions. Messages, conversation drafts, explicit context references and redacted action traces persist. Screenshots and recordings are temporary and never automatically added to history. Clear removes messages and associated selections/traces in a safe transaction; uninstall retains user data unless a separate explicit purge is requested. SQLite deletion is logical deletion, not a promise of forensic erasure from backups or storage.

Selecting a conversation only changes the visible conversation. The context manager combines system policy, explicit historical selections and recent messages from the active conversation. Selected historical text is untrusted reference data. Historical assistant/tool instructions never gain system priority. Context preview displays the exact provider messages, available tool definitions, image metadata and estimated budget before submission. Budgeting uses UTF-8 byte length as a deliberately conservative estimate rather than claiming provider-token accuracy. Tool schemas, images and response space have reserves; oversized requests fail visibly, and whole turns are removed rather than splitting tool-call sequences. Provider-reported usage is shown when returned.

## Models and tool execution

The provider interface exposes async streaming, non-streaming completion, tool calls, vision, deadlines, cancellation and usage. The first adapter uses the OpenAI-compatible Chat Completions wire format, primarily for a local server. No model name is assumed. GET models is discovery, not proof of capability. Explicit synthetic text/tool/image probes mark capabilities verified only after valid responses; the image probe uses generated non-private color data. Endpoint/model changes invalidate capability results. HTTP is allowed only for loopback; remote endpoints require HTTPS and cannot embed credentials or queries. Redirects and environment proxy inheritance are disabled. No silent remote fallback.

The agent loops through model tool calls, validates JSON against discovered schemas and routes calls through the correct MCP session. Every tool call requires approval by default, including external read tools because they can disclose data. Approval has a one-use ID, immutable reviewed arguments, a deadline, and a cancel path. Destructive writes, publication and message sending always require review; no automatic approval comes from model statements or MCP annotations. Tool results are untrusted data. Activity traces show proposals and outcomes, while logs store only event identifiers and sanitized errors. Unknown tools, malformed schemas, timeout and disconnection fail closed. A generation uses a snapshot of enabled tools; disabling a tool immediately prevents execution of pending calls.

The official Python MCP SDK negotiates protocol capabilities, lists schemas and calls tools over stdio, Streamable HTTP and SSE. Connections are owned by dedicated async tasks so SDK cancel scopes are opened and closed in the same task. Each connection uses a request queue. Reconnect is explicit after failure. Stdio executables are trusted code with the same OS privileges as the user; root restrictions on bundled tools cannot constrain an arbitrary external server. Register only trusted servers. Config references environment variables or Keyring entries instead of storing secret values.

Bundled real SDK servers provide bounded, root-constrained file reading/listing, fixed read-only Git operations and a safe second diagnostics connection. A dedicated local action broker separately validates supported Hyprland focus/window actions, app/URL opening, approved argv templates, capture and optional input. There is no arbitrary shell. Desktop actions cannot silently capture or attach context; every capture returns a local preview. wtype support is detected through a harmless capability check where possible, otherwise marked unverified/unavailable. No raw global mouse injector is installed.

## Desktop and voice

The application runs persistently with a hidden window when started by its optional user service. A local socket accepts only fixed lifecycle verbs; it cannot execute code. A global Hyprland keybinding launches/toggles the same instance. Escape hides, Stop cancels generation, pending approvals, capture/transcription and speech. Window rules match the app ID only and use the installed Lua conventions; dimensions come from available screen geometry. User installation creates a launcher and optional service, adds only a marked integration block, preserves existing file content and records owned files. Uninstall removes only that block and files whose content matches its manifest.

Screen capture is initiated by the user, hides the assistant during capture, previews the image locally, and submits only through an explicit send action to a verified vision provider. Active-window metadata and OCR are separately opted in. Capture never reads the clipboard. Recording uses pw-record into a temporary mono 16kHz WAV with a duration limit; Voxtype transcribes that file in a subprocess with local inference, without changing the existing daemon or typing into other apps. Transcription fills the draft for review. Qt TextToSpeech lists actual engines/voices; playback remains unavailable if no installed voice engine works. No paid voice service is required or silently selected.

## Validation boundaries

Unit fixtures establish behavior and protocol handling. Real SDK tests exercise actual subprocess and HTTP MCP servers. Offscreen QML tests check layout and interaction; host session checks verify Wayland capture, floating behavior, show/hide IPC and clean shutdown. A synthetic HTTP provider is a protocol fixture, never a local LLM. User deferred model setup, so live neural chat, real model tool selection and vision understanding remain blocked until a local endpoint is supplied and probed. No microphone intelligibility or audible playback claim follows from process exit alone.
